# Configuring Wreckfest game versions, offsets and chart defaults

Game-memory configurations now live in the same user-editable directory as
the form preferences:

```
%APPDATA%\PhysicsDataDebug\Settings\
```

On the **first launch**, the application creates
`WreckfestGameMemoryConfig.json` there using the defaults embedded in the
executable. The original source file is named `WreckfestGameMemoryConfig.json`
in the Visual Studio project and compiled as an **Embedded Resource**. You no
longer need a JSON file beside the executable. If you have an old, edited
`GameMemoryConfig.json` beside the executable from a previous release, that
file is copied to `WreckfestImportedGameMemoryConfig.json` and selected on the
first launch. The pristine `WreckfestGameMemoryConfig.json` remains available
separately. Existing AppData files are never overwritten by startup.

To edit the running game configuration, change its JSON in the AppData folder
and use **Config ▼ → Reload current configuration** on the Live Data page
while memory capture is stopped. Alternatively restart the app.

## Multiple game configuration profiles

Store any number of named game-memory JSON files in the Settings folder, for
example `WreckfestGameMemoryConfig.json` and
`WreckfestBetaGameMemoryConfig.json`. On the Live Data form, next to **Select
Game Version**, use **Config ▼**:

- **Load game configuration...** — select any JSON. If it is outside the
  Settings folder, a uniquely named copy is imported there first.
- **Save current configuration as...** — copy the current JSON to a new file
  for experimentation, without overwriting the original.
- **Reload current configuration** — apply manual edits to the active file.
- **Select Wreckfest configuration** — switch to the stored
  `WreckfestGameMemoryConfig.json`.
- **Open configuration folder** — open the AppData Settings folder.

Stop memory sampling and logging and close any other chart/settings forms
before switching. The available game versions and telemetry lists rebuild
from the newly loaded configuration. The selected filename is recorded in
`ActiveGameMemoryConfig.json` and restored automatically on later launches.
The regular `FormLiveData.json` independently remembers which **version** you
selected within that configuration. The original offsets and version options
are unchanged.

`ActiveGameMemoryConfig.json` is also editable. For example:

```json
{"fileName":"WreckfestGameMemoryConfig.json"}
```

It contains only a filename, not a full path. All selectable configurations
belong in `%APPDATA%\PhysicsDataDebug\Settings`. The current memory reader
still expects Wreckfest-style data layouts and the `Wreckfest_x64` process;
supporting a completely different game will also require adapting that reader.

## Configuration format (schema 2)

The bundled configuration now uses JSON **objects inside objects**, just as XML
can nest elements. There are eleven Wreckfest memory categories under
`categories`, and shared starting addresses under `baseAddresses`.

```json
{
  "schemaVersion": 2,
  "baseAddresses": {
    "vehicle": "0x18324C8",
    "engine": "0x18327C8",
    "timing": "0x1832648",
    "acceleration": "0x1832B88",
    "geometry": "0x184B118"
  },
  "categories": {
    "tire": {
      "base": "vehicle",
      "prefix": "WHEEL",
      "pointerOffsets": ["0xE78"],
      "wheelOffsets": {
        "FL": "0x0", "FR": "0xC50",
        "RL": "0x18A0", "RR": "0x24F0"
      },
      "fields": {
        "MomentOfInertia": "0x28",
        "SlipRatio": { "offset": "0xBF4", "absolute": true }
      }
    }
  }
}
```

This is an **illustrative fragment**, not a complete configuration. Use the
actual `WreckfestGameMemoryConfig.json` for all the other categories/fields.

A category's `base` refers to one of the addresses in `baseAddresses`; those
addresses already cover aliases shared between tire, suspension, aero, body
and differential groups. `pointerOffsets` is a sequence of pointer-chain
steps. For a wheel category, `wheelOffsets` gives the final wheel-relative
position. The field's `offset` is relative to the final resolved category
pointer, before the wheel-specific offset is added.

The existing internal `WF_*DataOffset` symbols are generated by the loader for
compatibility with chart and telemetry code. You do **not** write those tables
or `DataStart`/`ChunkSize` in schema 2.

## Adding a new tire telemetry field

**Simplest form:** Add one entry in `categories.tire.fields`:

```json
"MyNewTireValue": "0x4E0"
```

This reads a 32-bit floating-point value from the same pointer structure as
other tire values, separately for FL, FR, RL, and RR. It automatically appears
in the logging and chart field choices as appropriate (for example
`FL_MyNewTireValue` in combined logs; `MyNewTireValue` in a multi-wheel live
chart). You do not edit `telemetrySelections`.

**With field-specific settings:**

```json
"MyNewTireValue": {
  "offset": "0x4E0",
  "type": "float32",
  "absolute": true,
  "axisDefaults": {
    "min": -5.0,
    "max": 5.0,
    "majorInterval": 1.0,
    "decimals": 3,
    "minorEnabled": true,
    "minorIntervalFraction": 2
  }
}
```

`float32` is the default and can be omitted. Use `"type": "int32"`
when the raw four-byte value is a signed integer (as with RaceTime).
A field may also have an optional `alias` for the public prefixed name, e.g.
`"alias": "TireNewName"`. Do not include the FL/FR/RL/RR prefix yourself:
the application adds it for a wheel category.

## Adding calculated telemetry with JSON expressions

Calculated telemetry is configured alongside the raw fields in the same
category's `calculated` object. No memory offset is needed:

```json
"calculated": {
  "LateralFriction": {
    "expression": "div0(LateralLoad, VerticalLoad)",
    "absolute": true,
    "axisDefaults": {
      "min": -2, "max": 2, "majorInterval": 0.5,
      "decimals": 3, "minorEnabled": true,
      "minorIntervalFraction": 2
    }
  },
  "MyCombinedGrip": {
    "expression": "hypot(LateralFriction, LongitudinalFriction)"
  }
}
```

In this example, `MyCombinedGrip` is a **new** field. It automatically becomes
`FL_MyCombinedGrip`, `FR_MyCombinedGrip`, `RL_MyCombinedGrip`, and
`RR_MyCombinedGrip` in logging and Offline Chart. In multi-wheel live charts
it is shown once as `MyCombinedGrip`. You do not add it to another selection
list or write C#. Derived fields can reference other derived fields; the
application validates dependencies and detects cycles when loading the file.

Expressions support `+`, `-`, `*`, `/`, `%`, powers (`^`), parentheses,
unary signs, comparisons (`<`, `<=`, `>`, `>=`, `==`, `!=`), and Boolean
`&&`, `||`, `!`. Numeric constants use a **dot** as decimal separator.
Supported functions: `sqrt`, `abs`, `sin`, `cos`, `tan`, `asin`, `acos`,
`atan`, `atan2`, `min`, `max`, `pow`, `hypot`, `clamp`, `if`, `div0`,
`log`, `log10`, `exp`, `floor`, `ceil`, `round`, and `sign`. The named
physics functions `casterAngle`, `camberAngle`, `steerAngle`, `pitchAngle`,
`yawAngle`, and `rollAngle` accept the 16 matrix values (`M11` through
`M44`, row-major). `localX`, `localY`, and `localZ` accept those 16
body matrix values followed by a world-space X/Y/Z vector. Other functions
include `xzAngleRad(x,z)`, `normalizeXZAngle(angle)`,
`frictionAngleDeg(lateral,longitudinal)`, `loadSensGrip(load,power,offset)`,
`adhesionGrip(log10aT,speed)`, `microGrip(log10aT,speed)`, and
`macroGrip(log10aT,speed)`.

Constants: `pi`
and `e`. Angles supplied to trigonometric functions are in radians.
`div0(a,b)` returns zero if `b` is zero; ordinary `a/b` reports a
missing/invalid value on division by zero. `if(condition, yes, no)` only
calculates the chosen branch.

A simple field name like `VerticalLoad` resolves within its category. For a
measurement in a **different** category, use its canonical prefixed name:

```json
"PowerPerMass": {
  "expression": "ENG_EnginePowerKW / max(VEH_TotalMass, 1)"
}
```

This second example is illustrative: `VEH_TotalMass` must exist in your active
JSON, and its category must be supported. Cross-category names must exactly
match one of the canonical public telemetry names, including any field alias.
A formula in a wheel category is evaluated separately for each tire; you can
explicitly use `FR_SlipRatio` to access another wheel from a formula.

The included JSON defines **55 existing derived fields with expressions**,
including the quaternion/body transforms through reusable named functions.
`Log10aT` remains `"builtin": true` because it uses the specialized WLF
curve data. Existing schema 2 profiles without expressions can still use
legacy built-in formulas for recognized names; unknown new calculated fields
must specify an expression. You can replace `"builtin": true` with an
`"expression": "..."` for a recognized field. Schema 1 files continue using
their original built-in formulas.

Formulas are compiled once when the configuration is loaded, and calculated
**on demand** for only the telemetry that charts or loggers request. Offline
Chart uses the same formula definitions for imported files, but only when
all dependencies are present, and a recorded column always takes precedence.
Invalid expressions, missing dependencies, and calculation cycles are reported
as configuration errors. Runtime numeric failures are represented as invalid
values rather than aborting the logging session.

**Important:** Adding a raw field to an existing known category is
configuration-only. New memory structures, new categories, different value
widths (e.g., 8-byte doubles), and adding entirely new complex built-in functions still require
code changes. Ordinary arithmetic calculated fields do not. Offsets must be nonnegative and divisible by four.

## Automatic memory-read batching

The reader determines each category's minimum/maximum configured raw offsets
and builds small, contiguous read ranges from neighboring fields. It no longer
reads all the unused bytes between far-away offsets. It preserves a virtual
indexed 4-byte layout internally so the existing charts and formulas continue
to resolve field positions correctly.

The optional `readOptimization` section controls how nearby reads merge:

```json
"readOptimization": {
  "maxGapBytes": 32,
  "maxReadBytes": 4096
}
```

- `maxGapBytes`: include up to this many unused bytes between adjacent fields
  when combining them into one process-memory read (multiple of four, 0–1024).
- `maxReadBytes`: maximum combined read size (multiple of four, 4–1,048,576).

These settings change the number and size of memory-read calls, not the field
names or numeric offsets. The defaults balance call overhead and unnecessary
reads. If you make a previously working read fail due to inaccessible gaps,
reduce `maxGapBytes` to zero.

## Game versions

Every object under `versions` has an `id`, `displayName`, and `baseAddressShift`.
For example:

```json
{
  "id": "V1_308438",
  "displayName": "V1_308438",
  "baseAddressShift": "0x9E00",
  "enumOverrides": {}
}
```

The existing `enumOverrides` format is retained as a **backwards-compatible
advanced option**, referencing the generated internal category symbols. You
normally need only the version's base address shift. The shipped versions
are `V1_285308` (`0x0`) and `V1_308438` (`0x9E00`).

## Selections and defaults

`telemetrySelections` is no longer stored in schema 2: the program builds it
from all configured raw fields and the available calculated fields. Public
names use the appropriate telemetry prefix (`FL_`, `FR_`, `ENG_`, `BODY_`,
`TIME_`, etc.). The live Four Wheels form shows one relative tire field for
multi-wheel layouts and the selected wheel's prefix for a single-wheel layout.

`wheelAxisDefaults` and `absoluteValueFields` are no longer separate top-level
lists in schema 2. Their values live beside the field to which they apply.
Saved UI preferences still override configuration defaults until reset.

The `gForce` block remains:

```json
"gForce": {
  "gradientSteps": 10,
  "maxInfiniteHistoryPoints": 0
}
```

## Older JSON files and upgrading

The loader supports both **schema 1** (legacy `enumValues` and associated
lists) and **schema 2** (new grouped fields). Existing custom configs in your
AppData Settings folder are deliberately **not overwritten**. To use the new
schema with an existing installation, create or import a separate schema 2
configuration file through **Config ▼ → Load game configuration...**, then
select it. Preserve custom offsets and version overrides from your old file.

The `WreckfestGameMemoryConfig.json` embedded in the **new executable** is
schema 2, but it is copied to AppData only if that path does not already
exist. Rebuilding does not replace your existing AppData JSON automatically.

A JSON syntax error, an unknown category name, invalid field type, invalid
alignment, or missing required category produces a configuration error rather
than silently guessing memory addresses. Correctly formatted but incorrect
offsets can still read invalid memory: test new fields in game and keep a
working backup. No full Windows live-process test was performed for this
schema migration.

## Live Data display names and measurement units

Every schema 2 `fields` or `calculated` entry may include presentation metadata:

```json
"FrontLift": {
  "offset": "0x...",
  "displayName": "Front Lift",
  "unit": "N",
  "unitName": "newtons"
}
```

The `offset` in this example is illustrative: preserve the actual address in
WreckfestGameMemoryConfig.json. `displayName` is shown in Live Data; it never
renames the source field or CSV/logging header. `unit` is the short symbol
beside its live value, and `unitName` is the full text displayed on hover.
The shipped config includes display names for all raw and calculated fields,
and units for measurements whose units are known. Leave the unit blank for
unitless quantities or quantities whose physical meaning is not verified.

The Live Data form now has a category/measurement checkbox tree. Checking
Aerodynamics selects its drag and lift fields; individual fields may be
unchecked separately. Every monitored measurement occupies one row; tire and
suspension measurements display four wheel values on that row. Selections are
stored in `%APPDATA%\PhysicsDataDebug\Settings\LiveMonitorSelections.json`.
Fields added to the active JSON appear automatically the next time the config
is reloaded or the app is opened.
